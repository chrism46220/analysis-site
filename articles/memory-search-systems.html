How the Hybrid Engine Works

The agent tool memory_search runs both searches in parallel and fuses results:

User query "npm install failed with timeout"

    ├── Vector search ──────────────────────────────
    │    Query embedded → cosine distance against
    │    all chunk vectors → top-k by similarity
    │    (finds "npm ci --prefer-offline retry pattern")
    │
    ├── FTS5 keyword search ─────────────────────────
    │    BM25 ranking on tokenized query
    │    (finds "npm install ETIMEOUT error pattern")
    │
    └── Reciprocal Rank Fusion ──────────────────────
         Combines and re-ranks both result sets

Failure Modes

MCP Bridge is keyword-only. If you ask it "what happened with deploy last week?", it will search for those exact words in memory titles/content. It will not find a memory titled "staging pipeline failure on May 10" — it has no concept of semantic similarity. The agent's memory_search tool would find it by understanding the query's meaning.

Data Flow

Data stored in the MCP Bridge via memory_save is not automatically synced to the built-in search manager or vice versa. They are independent systems with different storage backends (separate SQLite databases, different indexing strategies).

Key Takeaway

Semantic search exists — but it lives in the built-in search manager and compiled wiki, not in the MCP bridge. The MCP bridge needs to be fed data that goes through the embedding pipeline to become semantically searchable, or it needs to be upgraded to use the same vector index.
