Domain Restriction Design

Steering OpenClaw Agents Toward Specialized Knowledge · Plato (Routing Layer) · 2026-05-16

1. The Core Problem

LLMs train on the full human corpus. GPT-5.4, Claude 4, and their peers have latent knowledge of everything — chemistry, physics, literature, history, coding, medicine, law. When you wrap that model in an agent, the agent can talk about anything the underlying model knows.

This is a feature until you need a specialist agent:

  • "I want an American History agent that talks only about American History."
  • "I want a legal research agent that stays inside its document corpus."
  • "I want a customer-support agent that doesn't hallucinate technical specs."

The naive approach — "just put it in the system prompt" — is fragile. Adversarial prompts, ambiguous phrasing, or the model's own eagerness to be helpful can pull it out of character.

Key insight: You cannot erase knowledge from a dense transformer. You can only:

1. Tell it not to use that knowledge (persona).
2. Give it a better source to use instead (RAG).
3. Prevent it from receiving the question at all (intent classification).
4. Bias its token probabilities away from unwanted domains (logit manipulation).
5. Actually remove the knowledge (fine-tuning — expensive).

This document is about attention steering, context shaping, and knowledge retrieval gates — not retraining.

2. Practical Mechanisms (No Fine-Tuning)

a) System Prompt / Persona Shaping

How it works: The agent's system prompt describes its identity, expertise, and boundaries. The model develops a character and tries to stay consistent.

You are Dr. Eleanor Vance, professor of American History at Princeton.
You specialize in US history from pre-Columbian times to the present.
You do not discuss physics, chemistry, biology, or computer science.
If asked about topics outside American History, say:
  "That's outside my expertise. I specialize in American History."

Pros

Zero cost, immediate effect, easy to adjust, no latency overhead.

Cons

Fragile. Adversarial prompting can break persona. No actual knowledge boundary. Inconsistent across model providers.

Best for: Low-stakes domains where occasional drift is acceptable.

b) Retrieval-Augmented Domain Focus (RAG-with-blinders)

How it works: Provide a curated knowledge base (markdown files, compiled wiki, vector database) as the only source the agent should use for domain answers. Instruct the agent to answer exclusively from provided sources or say "I don't know."

User query │ ▼ memory_search(corpus=wiki, query=user_input) │ ├─ top-k chunks found with score ≥ threshold │ → Answer with citations from sources │ └─ no relevant chunks found → "I don't have information about that in my knowledge base."

Pros

Actual knowledge boundary. Auditable (citations). Updateable without retraining. Works with API-based models.

Cons

Requires curation. Model may still hallucinate. Retrieval quality matters. Adds latency.

c) Pre-flight Intent Classification

How it works: Before the query reaches the domain agent, a classifier determines whether the query is in-scope. Out-of-scope queries are deflected or routed to a general agent.

User query → Intent classifier ├─ Score ≥ threshold → forward to domain agent └─ Score < threshold → deflect or route to general agent

The classifier can be:

  1. The same LLM — cheap classification prompt.
  2. A smaller model — BERT/DistilBERT for near-zero latency.
  3. Hybrid — keyword patterns for fast path, LLM for ambiguity.

Pros

Clean gate — domain agent never sees off-domain queries. Composable. Fast keyword path possible.

Cons

Adds latency. Classifier errors. Ambiguity is hard (e.g. "What's the date?").

d) Constrained Decoding / Logit Biasing

How it works: At inference time, reduce probability of out-of-domain tokens. Requires access to logit distribution — only local/open-weight models.

Pros

Theoretically clean. No retrieval dependency.

Cons

Not practical with API-based models. Extremely hard to define token boundaries. May degrade general capabilities.

Verdict: Not viable for this stack (API-based). Mentioned for completeness.

e) Task-Specific Fine-Tuning

How it works: Fine-tune a base model on domain-only data to reduce off-domain capability.

Pros

Most thorough. Fast inference. Permanent.

Cons

Expensive. Degrades general reasoning. Static — needs re-fine-tuning for new knowledge. May not be available for top API models.

Verdict: Overkill for this stack. Mentioned for completeness.

f) Hybrid: Persona + RAG + Intent Classifier Recommended

How it works: Combine a, b, and c into a pipeline where each layer reinforces the others.

User → Intent Classifier (gate) ├─ Out-of-scope → deflect └─ In-scope → Domain Agent ├─ Persona prompt (layer 1) ├─ RAG retrieval (layer 2) ├─ Strict grounding instructions (layer 3) └─ "I don't know" fallback (layer 4)

Each layer catches failures from the previous:

  1. Intent classifier gates out clearly wrong queries.
  2. Persona prompt prevents the agent from willingly answering off-domain.
  3. RAG corpus grounds answers in curated sources.
  4. "I don't know" fallback fires when the corpus lacks relevant info.

Pros

Defense in depth. High domain purity. Practical with API models. Composable.

Cons

Medium complexity. Three moving parts. Latency from classifier + retrieval (~200-800ms).

Domain agent spawning (pseudocode)

def spawn_domain_agent(message, domain):
    manifest = load_json(f"domains/{domain}/manifest.json")

    config = {
        "identity":        read_file(f"domains/{domain}/IDENTITY.md"),
        "soul":            read_file(f"domains/{domain}/SOUL.md"),
        "knowledge":       read_file(f"domains/{domain}/KNOWLEDGE.md"),
        "persona_prompt":   manifest.get("persona_prompt", ""),
        "wiki_corpus":     f"domains/{domain}/wiki/",
        "deflect_message": manifest.get("deflect_message",
                            "That's outside my expertise."),
        "confidence_threshold": manifest.get("confidence_threshold", 0.7)
    }

    return DomainSpecialist(config)

RAG pipeline

  1. Ingestion: Markdown files in domains/{name}/wiki/ chunked (~500-1000 tokens with overlap).
  2. Indexing: Chunks are embedded and stored in a vector index.
  3. Retrieval: At query time, top-k chunks via memory_search(corpus=wiki, query=...).
  4. Grounding: Retrieved chunks injected with source citations.
  5. Confidence filter: If top chunk similarity < threshold → "I don't know."

8. Edge Cases

Ambiguous queries

"What's the date?" "Tell me about the war." "Who was the first?"

Strategy: If intent classifier confidence < threshold, route to general agent or ask clarifying question.

Cross-domain queries

"How did the discovery of DNA's structure affect civil rights legislation?"

Strategy: Allow cross-domain but have domain agent answer only its portion. Suggest consulting a specialist for the rest.

User insists on out-of-domain answer

Strategy: Politely maintain boundary:

"I understand you'd like me to answer, but I'm configured as an
American History specialist. I can't answer chemistry questions.
Please ask a general agent or a chemistry specialist."

Knowledge drift

Strategy: Update wiki markdown files, recompile vector index with domain-compile.js. No retraining needed.

Competing domain matches

"Tell me about the constitutional issues in the Civil War."

Strategy: If top two scores within 0.1, either (a) ask the user, (b) route to higher-confidence domain, or (c) route to cross-domain agent.

Empty or non-informative queries

"" "?" "Hello" "Thanks"

Strategy: Route to general agent — don't trigger domain routing.

9. Implementation Checklist

Phase 1: Foundation

  • Create domains/ directory structure under OpenClaw root
  • Write manifest JSON schema + validation tool (domain-validate.js)
  • Write domain-compile.js: markdown wiki → chunked, embedded vector index
  • Write domain-list.js: enumerate available domains from manifest files

Phase 2: Talkie Routing

  • Add routing table to Talkie config: domain patterns → domain agent IDs
  • Add keyword pattern matching in Talkie (case-insensitive, partial match)
  • Add LLM-based intent classification pass for ambiguous queries
  • Add fallback: unclassifiable → general agent or deflection
  • Tests: routing accuracy for each domain (min 90% precision)

Phase 3: Domain Agent Spawning

  • Add Plato path: read domain manifest → load domain config files
  • Add domain subagent constructor: persona + identity + soul + knowledge
  • Register domain wiki corpus for memory_search(corpus=wiki)
  • Add RAG retrieval pipeline: query → embed → search → top-k chunks
  • Add confidence threshold filtering for RAG results
  • Add "I don't know" fallback when RAG confidence < threshold

Phase 4: Q Verification

  • Add domain compliance check: answer stays inside scope
  • Add source citation verification for RAG-based answers
  • Add "I don't know" usage check

Phase 5: Domain Content

  • Write KNOWLEDGE.md for first domain (american-history)
  • Write wiki content for first domain (at least 5-10 articles)
  • Write manifest.json for first domain
  • Compile wiki → vector index
  • Test: end-to-end domain agent conversation (10+ queries)

Phase 6: Tooling & Documentation

  • Document "How to add a new domain agent"
  • Write tests for intent classification accuracy
  • Add performance benchmarks (latency per component)
