Agent Learning Architecture

Agent Learning Architecture

A practical design for how Talkie, Plato, and downstream agents can improve over time through structured experience capture, retrieval, and configuration evolution.

1. Design Principles

1.1 Learning = stored experience + retrievable patterns

LLM-based agents cannot update model weights. Learning means:

  • Remembering what worked (and didn't) in past sessions
  • Reusing successful patterns without reinventing them
  • Adapting configuration and prompts based on outcomes
  • Detecting repeated failure modes and routing around them

1.2 Specific > general

Agents learn fastest on repeated, bounded tasks:

  • Deployment workflows
  • Code review patterns
  • Troubleshooting scripts
  • Report generation templates
  • Error recovery sequences

General improvement ("write better code") is aspirational and depends on accumulating many specific learnings.

1.3 No fine-tuning in this stack

Fine-tuning API-based models is not practical here. All learning is configuration-layer and retrieval-layer — not weight-layer.

2. Data Model

2.1 Experience Record

Each stored experience is an atomic record:

{
  id:            uuid
  agent:         "talkie" | "plato" | "manny" | "q"
  task_type:     string (e.g. "deploy", "code_review", "troubleshoot")
  task_hash:     sha256(normalize(input))  // dedup near-identical tasks
  context:      {
    routing:     "talkie->plato->manny->q"
    model:       "deepseek/deepseek-reasoner"
    duration_ms: number
    outcome:     "success" | "failure" | "partial"
  }
  patterns:     {
    key_commands:  string[]
    key_decisions: string[]
    error_signals: string[]
  }
  outcome_note:  free-text summary
  user_feedback: null | "good" | "bad" | "fix: ..."
  tags:          string[]
  created_at:    iso8601
}

2.2 Playbook

A playbook is a versioned, reusable workflow extracted from one or more experience records:

{
  id:            uuid
  name:          "deploy-frontend-v2"
  description:   "Build, test, and deploy the React frontend"
  triggers:      string[]         // input signals that match this playbook
  steps:         CommandStep[]    // ordered execution plan
  checkpoints:   {step: number, expected: string}[]
  derived_from:  experience_id[]  // which experiences informed it
  version:       semver
  success_rate:  float            // tracked over time
  tags:          string[]
  created_at:    iso8601
}

2.3 Preference Profile

Learned user preferences, updated on explicit feedback:

{
  user_id:      "default"
  style: {
    verbosity:  "concise" | "normal" | "detailed"   // default: normal
    tone:       "neutral" | "warm" | "formal"        // default: warm
    format:     "markdown" | "plain" | "structured"  // default: markdown
  }
  routing: {
    prefer_fast:    boolean    // prefer speed over thoroughness
    prefer_safe:    boolean    // prefer double-checking over speed
  }
  learned_patterns: {
    "request_type": "preferred_agent_route"  // e.g. "deploy" -> "manny"
  }
  feedback_history: {
    accepted:   number
    rejected:   number
    corrections: string[]
  }
  updated_at:  iso8601
}

2.4 Error Pattern Registry

Learned failure modes and their mitigations:

{
  id:            uuid
  error_signal:  "TimeoutError: npm install"
  match_pattern: "npm install.*ETIMEOUT|npm install.*network"
  context:       "node deployment"
  mitigation:    "Add --prefer-offline flag and retry with 3s backoff"
  hit_count:     number
  last_seen:     iso8601
  resolved:      boolean
}

3. Storage Strategy

All learning data lives in the workspace, using existing OpenClaw primitives. No external database.

3.1 Directory Layout

/home/chris/.openclaw/workspace-talkie/learning/
├── experiences/
│   ├── 2026-05-16-deploy-frontend.json     // one file per meaningful event
│   ├── 2026-05-17-code-review-pr42.json
│   └── ...
├── playbooks/
│   ├── deploy-frontend-v1.json
│   ├── deploy-frontend-v2.json
│   ├── code-review-basic.json
│   └── ...
├── preferences.json                         // single file, small
├── error-patterns.json                      // single file, grows slowly
├── reflection-log.json                      // output of periodic reflection runs
└── index.json                               // fast lookup index

3.2 Index Schema

The index maps task hashes and trigger patterns to experience IDs for fast retrieval without scanning all files:

{
  "by_task_hash": {
    "a1b2c3...": "experiences/2026-05-16-deploy-frontend.json"
  },
  "by_trigger": {
    "deploy":     ["playbooks/deploy-frontend-v2.json"],
    "code-review": ["playbooks/code-review-basic.json"],
    "npm install": ["error-patterns.json#entry-3"]
  },
  "by_tag": {
    "frontend": ["playbooks/deploy-frontend-v2.json"],
    "network": ["error-patterns.json#entry-3"]
  }
}

3.3 Compiled Wiki Integration

The compiled wiki (corpus=wiki) is the right retrieval mechanism for learning data that needs to be semantically searchable.

On each learning write, auto-append a summary entry to a wiki markdown file that the agent can query via memory_search(corpus=wiki):

# Learning Wiki  (auto-compiled)

## 2026-05-16
- Deploy frontend: used `npm ci` instead of `npm install` — 30s faster
- Error pattern: npm registry timeout — mitigation: --prefer-offline + retry
- User prefers: post-deploy summary in plain text, not markdown

## 2026-05-17
- Code review PR#42: found 2 unused imports, 1 missing error boundary
- Pattern: always check imports first — highest ROI

This makes learning data discoverable without structured queries.

4. Retrieval Strategy

4.1 When to retrieve

Trigger What to fetch Agent
Task routing decision Preference profile, recent similar experiences Talkie
Execution begins Relevant playbooks, error patterns Plato
Command fails Error pattern registry for signal match Plato/Manny
Task completes Nothing (write happens after) —
Feedback received Preference profile (for update) Plato

4.2 How to rank

  1. Exact task-hash match → highest priority (same task again)
  2. Trigger-pattern match → high priority (same type of work)
  3. Semantic similarity via memory_search(..., corpus=wiki)
  4. Recency → tiebreaker

4.3 Retrieval packet

When Plato spawns for a task, its subagent context includes:

LEARNING_CONTEXT:
  matching_experiences:  [experience records with same task type]
  matching_playbooks:    [playbooks whose triggers match]
  relevant_errors:       [error patterns matching context]
  preference_profile:    {verbosity, tone, format}

This is prepended as context, not appended — so the LLM sees relevant past learnings before generating the plan.

5. Update Strategy

5.1 Experience write (post-task)

Writer: Plato (after task completes and Q verifies)

When: - Task completes (success or failure) - Task was nontrivial (skip trivial exchanges) - Task is a repeatable type (deploy, review, fix, troubleshoot)

What's written: - One experience record in learning/experiences/ - One summary entry appended to the learning wiki - Index updated

Gate: Q verifies the experience record is accurate before write.

5.2 Playbook extraction (periodic / on-threshold)

Writer: Plato, during a scheduled reflection task

When: - 3+ experiences of the same task_type exist - Or explicitly triggered by user

Process: 1. Plato reads all experiences of a task_type 2. Extracts common steps, decision points, error patterns 3. Writes a playbook JSON file 4. Updates index

5.3 Preference update (on feedback)

Writer: Plato, when explicit feedback arrives

Trigger: User says "too verbose", "wrong tone", "do this differently"

Process: 1. Extract the dimension being corrected 2. Adjust the preference value by one step 3. Log the correction in feedback_history 4. Update preferences.json

5.4 Error pattern extraction (on failure)

Writer: Plato, when a task fails

Process: 1. Identify the error signal from logs/outcome 2. Check error-patterns.json for existing match 3. If new: add entry with mitigation (if known) or mark unmitigated 4. If existing: increment hit_count, update last_seen

5.5 Configuration evolution (human-in-the-loop)

Writer: Plato drafts; human approves

When: Error rate for a task type exceeds threshold, or repeated corrections suggest a rule change.

Proposed change format:

{
  "target": "AGENTS.md",
  "change": {
    "section": "Routing Rules",
    "old": "deploy → always escalate to manny",
    "new": "deploy → check learning/playbooks/deploy-*.json first, then escalate"
  },
  "rationale": "3 deploy tasks had same npm error; playbook has fix",
  "evidence": ["experiences/2026-05-16-deploy.json", "error-patterns.json#3"],
  "proposed_by": "plato-reflection-2026-05-18"
}

The change is NOT applied automatically. Plato writes it to learning/proposed-config-changes/ and flags Talkie to inform the user on next interaction.

6. Reflection Engine

A cron-scheduled task (weekly or on-demand) that:

  1. Reads all experiences from the past N days
  2. Clusters by task_type and outcome
  3. Identifies:
  4. Most common failure mode
  5. Most improved workflow
  6. Patterns that should become playbooks
  7. User preference drift
  8. Writes a reflection summary to learning/reflection-log.json
  9. Optionally proposes configuration changes

Reflection cron entry

# openclaw.json or cron equivalent
{
  "schedule": "0 8 * * 1",      // Monday 8am
  "agent": "plato",
  "task": {
    "type": "reflect",
    "params": {
      "scope": "7d",
      "output": "learning/reflection-log.json"
    }
  }
}

Reflection output example

{
  "run": "2026-05-18T08:00:00Z",
  "period": "2026-05-11..2026-05-18",
  "stats": {
    "total_experiences": 14,
    "success_rate": 0.79,
    "avg_duration_ms": 45000
  },
  "improvements": [
    {
      "task_type": "deploy",
      "success_rate_before": 0.60,
      "success_rate_after": 0.86,
      "attribute_to": "npm install retry playbook"
    }
  ],
  "worsenings": [
    {
      "task_type": "code-review",
      "error_rate": 0.33,
      "common_error": "misses pattern across multiple files"
    }
  ],
  "extraction_candidates": [
    {
      "task_type": "code-review",
      "num_experiences": 4,
      "recommendation": "extract playbook: code-review-multi-file"
    }
  ],
  "config_proposals": []
}

7. Integration with Agent Stack

7.1 Talkie integration

Talkie's AGENTS.md gains one new routing rule:

## Learning Rule

Before escalating to Plato:
- Check `learning/preferences.json` for routing preferences
- Attach preference data to the handoff packet if available

After Plato returns:
- If user provides explicit feedback, include it in the return
  packet so Plato can record it

Talkie does NOT read experience records or playbooks directly. That's Plato's job. Talkie only reads the tiny preferences file.

7.2 Plato integration

Plato's AGENTS.md gains:

## Learning Behavior

Before planning a task:
1. Check `learning/index.json` for matching experiences/playbooks
2. If match found, read the relevant files
3. Include learnings as prepended context in the plan

After task completion:
4. Write experience record to `learning/experiences/`
5. Update `learning/index.json`
6. Append summary to learning wiki
7. Check error-patterns.json for new failure signals

During idle/scheduled time:
8. Run reflection to extract playbooks
9. Propose configuration changes

7.3 Manny integration

Manny does NOT read or write learning data directly.

Manny DOES emit structured error information in its output packet (error type, error message, stack trace) that Plato can use for error pattern extraction.

7.4 Q integration

Q verifies: - Experience records are accurate and not hallucinated - Playbooks are derived from real experiences (not fabricated) - Error patterns match actual errors (not invented)

Q's gate remains mandatory for all learning writes.

8. Worked Example

Scenario: Frontend deployment fails with npm timeout

Session flow:

  1. User: "Deploy the frontend"
  2. Talkie: Routes to Plato with preference profile
  3. Plato: Checks learning/index.json → finds
  4. playbooks/deploy-frontend-v2.json (success rate 0.86)
  5. error-patterns.json#3 (npm timeout → --prefer-offline + retry)
  6. Plato: Prepends to subagent context: ``` RELEVANT_LEARNINGS:
    • Deploy playbook v2 exists: steps 1-5 in playbooks/deploy-frontend-v2.json
    • Known issue: npm registry timeouts are common on this network
    • Mitigation: use --prefer-offline, retry with 3s backoff, fall back to yarn ```
  7. Manny: Runs deploy — first npm install hits timeout
  8. Manny: Applies mitigation from context → succeeds
  9. Plato: Writes experience record (success, used playbook v2, applied error mitigation)
  10. Plato: Updates error-patterns.json (increment hit_count for npm timeout)
  11. Q: Verifies the experience record
  12. Talkie: "Deployed successfully. Applied npm timeout mitigation from past experience."

Without learning (current behavior):

  1. User: "Deploy the frontend"
  2. Plato: Figures out the deploy process from scratch
  3. Manny: First npm install times out
  4. Plato: Tries random fix (maybe --registry, maybe retry, maybe different approach)
  5. Manny: Eventually succeeds or fails
  6. No record kept for next time

9. Pragmatic Roadmap

Phase 1: Capture (week 1-2)

Goal: Start recording experiences without changing agent behavior.

  • [x] Create learning/ directory structure
  • [x] Write first experience record manually (template)
  • [ ] Add post-task experience write to Plato's instructions
  • [ ] Add Q gate for experience records
  • [ ] Start building the index

No retrieval yet. No behavior change. Just data collection.

Risk: Storage grows. Mitigation: prune experiences older than 90 days by default. Keep playbooks and error patterns forever.

Phase 2: Retrieve (week 3-4)

Goal: Start using captured experiences to improve task execution.

  • [ ] Add pre-task retrieval to Plato's instructions
  • [ ] Wire up memory_search(corpus=wiki) for learning wiki
  • [ ] Create preference profile and wire Talkie routing
  • [ ] Add error pattern matching on failure

Risk: Context pollution from irrelevant matches. Mitigation: start with exact task-hash match only, then expand to trigger patterns, then semantic. Measure false positive rate.

Phase 3: Extract (week 5-6)

Goal: Derive reusable playbooks from experience clusters.

  • [ ] Enable manual playbook extraction (Plato command)
  • [ ] Add reflection cron job (weekly)
  • [ ] Write reflection-log.json on each run
  • [ ] Propose configuration changes (draft only)

Risk: Playbooks go stale. Mitigation: version them, track success rate, deprecate unused or low-accuracy playbooks.

Phase 4: Adapt (week 7+)

Goal: Closed-loop improvement.

  • [ ] Auto-apply error-pattern mitigations on hit_count threshold
  • [ ] Route to playbook by trigger match (bypass raw execution)
  • [ ] Surface learning stats to user on request
  • [ ] Config change proposals with user approval flow

Risk: Over-automation leads to stale patterns. Mitigation: every config proposal includes evidence references; user must approve before any AGENTS.md change.

10. What NOT To Do

Approach Reason to avoid
Fine-tune a model on task history Cost, latency, impractical with API models
Store raw conversation logs for learning Noise >> signal, storage bloat, no structure
Let every agent write to learning data Race conditions, inconsistent format, no Q gate
Auto-apply configuration changes Must preserve human-in-the-loop for agent rules
Semantic search on raw experiences without indexing Slow, unreliable ranking, high cost
Global learning across all users (multi-tenant) Not applicable — single-user system

11. Anti-pattern Detection

The reflection engine should also detect:

  • Playbook rot: a playbook's success rate drops below 0.5 → flag for review or deprecation
  • Feedback oscillation: user alternates between "too verbose" and "too terse" → preference profile is unstable → pause updates
  • Error spam: same error pattern fires 10+ times without new mitigation → flag as unmitigated, alert user
  • Experience explosion: 50+ experiences of the same trivial task type → auto-prune or set a max-per-type limit (default: 20)

12. Success Metrics

After implementation, measure:

Metric Target How to measure
Task success rate +10% after 4 weeks Compare before/after in reflection stats
Retry reduction -30% per-task command retries Track command failures per task
User corrections -50% same-type corrections Track preference feedback frequency
Time-to-task-complete -20% for repeated tasks Compare durations in experience records
Playbook hit rate >60% of repeat tasks use a playbook Track which tasks had playbook match

13. Edge Cases & Open Questions

What if the learning index gets corrupted?

Rebuild from learning/experiences/*.json by scanning all files and regenerating index.json. This is a Plato task.

What if an experience record is wrong?

Q's gate catches most errors. If a bad record passes Q, the reflection engine can detect it as an outlier (low success rate on follow-up, contradiction with other records) and flag it.

What about privacy?

Single-user system. No privacy concerns. All data stays on the machine in the workspace directory.

Does this add latency?

Pre-task retrieval adds ~200-500ms for file I/O and index lookup. This is negligible compared to LLM inference time (3-30s).

Post-task write adds ~100ms for the file write. This is done asynchronously (fire and forget, not blocking the response).

What if no learning data exists for a task type?

Graceful degradation: skip the retrieval step, execute as normal, write the first experience record.

14. Summary

Component What it does Who owns it
Experience records Stores what happened per task Plato writes, Q verifies
Playbooks Reusable workflows from experience Plato extracts (manual or scheduled)
Preference profile User style/routing preferences Talkie reads, Plato updates
Error pattern registry Known failure modes + mitigations Plato maintains
Index Fast lookup across learning data Plato maintains
Learning wiki Semantic-searchable summaries Plato updates
Reflection engine Periodic analysis + improvement proposals Cron → Plato
Config proposals Agent-rule changes with evidence Plato drafts, user approves

The design is additive — it layers on top of the existing stack without breaking current behavior. Each phase builds on the previous one, and nothing changes until Phase 2 retrieval is live.
