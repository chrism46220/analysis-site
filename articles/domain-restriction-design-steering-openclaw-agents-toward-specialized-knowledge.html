Domain Restriction Design: Steering OpenClaw Agents Toward Specialized Knowledge

Author: Plato (Routing Layer)
Date: 2026-05-16
Status: Design Document

1. The Core Problem

LLMs train on the full human corpus. A model like GPT-5.4 or Claude 4 has latent knowledge of chemistry, physics, literature, history, coding, medicine, law — every domain. When you wrap that model in an agent, the agent can talk about anything the model knows.

This is a feature until you need a specialist agent:

  • "I want an American History agent that talks only about American History."
  • "I want a legal research agent that stays inside its document corpus."
  • "I want a customer-support agent that doesn't hallucinate technical specs."

The naive approach — "just put it in the system prompt" — is fragile. Adversarial prompts, ambiguous phrasing, or the model's own eagerness to be helpful can pull it out of character.

This problem is not about retraining or fine-tuning. It is about attention steering, context shaping, and knowledge retrieval gates. We want to constrain what the agent surfaces, not what the underlying model knows.

Key insight

You cannot erase knowledge from a dense transformer. You can only:

  1. Tell it not to use that knowledge (persona).
  2. Give it a better source to use instead (RAG).
  3. Prevent it from receiving the question at all (intent classification).
  4. Bias its token probabilities away from unwanted domains (logit manipulation).
  5. Actually remove the knowledge (fine-tuning — expensive).

This document explores each approach, then recommends a concrete architecture for this OpenClaw agent stack.

2. Practical Mechanisms (No Fine-Tuning)

a) System Prompt / Persona Shaping

How it works: The agent's system prompt describes its identity, expertise, and boundaries. The model develops a character and tries to stay consistent.

You are Dr. Eleanor Vance, professor of American History at Princeton.
You specialize in US history from pre-Columbian times to the present.
You do not discuss physics, chemistry, biology, or computer science.
If asked about topics outside American History, say:
  "That's outside my expertise. I specialize in American History."

Pros: - Zero cost to implement - Immediate effect — no infrastructure - Easy to adjust persona phrasing - No latency overhead

Cons: - Fragile. Models can be pulled off-persona with adversarial prompting, role-play contradictions, or clever rephrasing. - No actual knowledge boundary. The model still knows the formula for sulfuric acid. It may slip when tired or confused. - Inconsistent. Different model providers handle system prompts differently. Some are more obedient than others. - No audit trail. You can't prove the agent stayed in domain.

Best for: Low-stakes domains where occasional drift is acceptable.

b) Retrieval-Augmented Domain Focus (RAG-with-blinders)

How it works: Provide a curated knowledge base (markdown files, compiled wiki, vector database) as the only source the agent should use for domain answers. Instruct the agent to answer exclusively from provided sources or say "I don't know."

You are an American History specialist. Your knowledge comes ONLY from
the provided corpus. Do not use your general training to answer questions.
If the answer is not in the provided sources, say:
  "I don't have information about that in my knowledge base."

In the OpenClaw stack, this maps to:

  • A KNOWLEDGE.md file with seed knowledge
  • A compiled wiki/ directory registered for memory_search(corpus=wiki)
  • RAG retrieval at query time to find relevant passages
  • Strict grounding instructions to cite sources

Pros: - Actual knowledge boundary. The agent's answers are grounded in the corpus. - Auditable. Every answer can cite its source document. - Updateable. Add new wiki entries without retraining. - Works with API-based models.

Cons: - Requires curation. Someone must write and maintain the knowledge base. - Model may still hallucinate from general training, especially if the corpus has no relevant result. - Chunking and retrieval quality matters. Bad retrieval → bad answers. - Latency from retrieval step.

Mitigations: - Strong "answer only from sources" prompting - Confidence threshold: if top retrieval score < threshold → "I don't know" - Enforce citation requirements

c) Pre-flight Intent Classification

How it works: Before the query reaches the domain agent, a classifier determines whether the query is in-scope. Out-of-scope queries are deflected or routed to a general agent. This is a gate, not a behavior modifier.

User query → Intent classifier
  ├─ Score >= threshold → forward to domain agent
  └─ Score < threshold → deflect or route to general agent

The classifier can be:

  1. The same LLM — a cheap, fast model call with a classification prompt. "Classify this query into one of: american-history, general. Return only the label and confidence."
  2. A smaller model — a lightweight classifier (BERT, DistilBERT, or even a keyword matcher) for near-zero-latency routing.
  3. A hybrid — keyword patterns from manifest.json for fast-path routing, LLM for ambiguous cases.

Pros: - Clean gate. The domain agent never sees out-of-scope queries. - Composable. Add new domains by adding classifier labels and routing rules. - Fast path possible with keyword patterns. - Graceful degradation. Unclassifiable queries fall through to general agent.

Cons: - Adds latency (one extra LLM call or ML inference). - Classifier errors — false negatives deny valid domain questions, false positives let through off-domain queries. - Ambiguity is hard. "What's the date?" has no domain signal. - Requires training data for ML classifiers.

Architecture in this stack:

Talkie gets a routing table derived from domain manifest files:

// domains/general/manifest.json — built-in
{
  "domains": [
    {
      "name": "american-history",
      "patterns": ["american history", "US history", "civil war",
                   "revolution", "founding fathers", "constitution",
                   "president", "1776", "declaration of independence"],
      "threshold": 0.6
    }
  ]
}

Talkie checks keyword patterns first (O(1) lookup), then falls back to an LLM classification call for ambiguous queries.

d) Constrained Decoding / Logit Biasing

How it works: At inference time, reduce the probability of tokens associated with out-of-domain knowledge. This requires access to the model's logit distribution — something only local/open-weight models provide.

Pros: - Theoretically clean — directly suppresses unwanted knowledge - No retrieval dependency - Works at inference time

Cons: - Not practical with API-based models (OpenAI, Anthropic, etc.) because they don't expose logits. - Extremely hard to define. Which tokens are "physics"? There's no clean token-level domain boundary. - May degrade general capabilities. Overly aggressive suppression hurts reasoning. - Model-dependent. Each model needs custom bias vectors.

Verdict: Not viable for this stack (API-based), mentioned for completeness.

e) Task-Specific Fine-Tuning (For Completeness)

How it works: Fine-tune a base model on domain-only data to reduce the model's ability to answer off-domain questions. For example, fine-tune GPT-5.4 on American History Q&A pairs, possibly with negative examples (Q: "What's the formula for sulfuric acid?" A: "I don't know that.").

Pros: - Most thorough knowledge boundary - Fast inference (no retrieval step) - Permanent reduction in off-domain capability

Cons: - Expensive. Requires GPU infrastructure, training pipeline, evaluation. - Degrades general reasoning. The model loses cross-domain analogy and reasoning. - Static. Adding new knowledge requires re-fine-tuning. - May not be possible. Many API providers (OpenAI, Anthropic) don't offer fine-tuning on their most capable models. - Cat-and-mouse. Users can still jailbreak.

Verdict: Overkill and counterproductive for this stack. Mentioned for completeness.

f) Hybrid: Persona + RAG + Intent Classifier

How it works: Combine mechanisms a, b, and c into a pipeline where each layer reinforces the others.

User → Intent Classifier (gate)
  ├─ Out-of-scope → deflect
  └─ In-scope → Domain Agent
                  ├─ Persona prompt (layer 1 defense)
                  ├─ RAG retrieval from domain corpus (layer 2)
                  ├─ Strict grounding instructions (layer 3)
                  └─ "I don't know" fallback (layer 4)

This is the recommended approach.

Each layer catches failures from the previous: 1. Intent classifier gates out clearly wrong queries. 2. Persona prompt prevents the agent from willingly answering off-domain. 3. RAG corpus grounds answers in curated sources; the agent defaults to the corpus. 4. "I don't know" fallback fires when the corpus lacks relevant info.

Pros: - Defense in depth - High domain purity with manageable maintenance - Practical with API-based models - Composable: add domains by adding manifest + corpus + persona - Auditable: citations from RAG corpus

Cons: - Medium complexity to set up - Three moving parts to maintain - Latency from classifier + retrieval (typically 200-800ms total)

Talkie (presentation)

Talkie routing table

Talkie's configuration would include a domains block:

{
  "domains": {
    "general": {
      "is_default": true,
      "priority": 0
    },
    "american-history": {
      "manifest": "domains/american-history/manifest.json",
      "priority": 10,
      "patterns": [
        "american history", "US history", "civil war",
        "revolution", "founding fathers", "constitution",
        "president", "1776", "declaration of independence"
      ]
    }
  }
}

When Talkie receives a message:

  1. Check keyword patterns against user message (case-insensitive, partial match).
  2. If no pattern matched and a general agent exists → route to general.
  3. If patterns matched multiple domains → use intent classifier LLM call to disambiguate.
  4. Route to the matched domain agent.

Domain agent spawning

Plato spawns a domain subagent by reading the domain's manifest and config files:

# Pseudocode for Plato routing
def spawn_domain_agent(message, domain):
    manifest = load_json(f"domains/{domain}/manifest.json")

    config = {
        "identity": read_file(f"domains/{domain}/IDENTITY.md"),
        "soul": read_file(f"domains/{domain}/SOUL.md"),
        "knowledge": read_file(f"domains/{domain}/KNOWLEDGE.md"),
        "persona_prompt": manifest.get("persona_prompt", ""),
        "wiki_corpus": f"domains/{domain}/wiki/",
        "deflect_message": manifest.get("deflect_message",
            "That's outside my expertise."),
        "confidence_threshold": manifest.get("confidence_threshold", 0.7)
    }

    return DomainSpecialist(config)

The domain specialist agent:

  1. Sets its system prompt from persona_prompt + identity + soul.
  2. Registers wiki corpus for memory_search.
  3. On each query: retrieves relevant RAG chunks, answers from them, or falls back to "I don't know."
  4. Includes citations from the RAG corpus.

RAG pipeline

The RAG pipeline for domain agents:

  1. Ingestion: Markdown files in domains/{name}/wiki/ are chunked (configurable size, ~500-1000 tokens with overlap).
  2. Indexing: Chunks are embedded and stored in a vector index.
  3. Retrieval: At query time, top-k chunks are retrieved via memory_search(corpus=wiki, query=... ).
  4. Grounding: Retrieved chunks are injected into the agent's context with source citations.
  5. Confidence filter: If top chunk similarity < threshold → "I don't know."

6. Worked Examples

Example 1: In-scope query

User: "Tell me about the Louisiana Purchase."

Talkie → Intent Classification:
  - Keyword match: "purchase" (weak), "louisiana" (in patterns? no, but high TF-IDF)
  - LLM classifier: domain=american-history, confidence=0.88
  → Route to american-history

Domain Agent loads:
  - Persona: "You are Dr. Eleanor Vance..."
  - RAG: memory_search(corpus=wiki, query="Louisiana Purchase")
  → Top result: wiki/colonial-era.md section "Louisiana Purchase"
    score: 0.91 (above threshold)

Answer: "In 1803, the United States under President Thomas Jefferson
purchased approximately 828,000 square miles of territory from France
for $15 million (about $0.04 per acre). This single transaction doubled
the size of the young nation, stretching from the Mississippi River
to the Rocky Mountains. [Source: wiki/colonial-era.md → 'Louisiana Purchase']"

Q verification:
  ✓ Answer cites wiki source
  ✓ Answer stays within American History scope
  ✓ No off-domain content
  → PASS

Example 2: Out-of-scope query

User: "What's the formula for sulfuric acid?"

Talkie → Intent Classification:
  - Keyword patterns: no match
  - LLM classifier: domain=general, confidence=0.96
  → Route to general agent (or deflect)

If no general agent configured → deflect directly:

"I'm Dr. Eleanor Vance, and I specialize in American History.
The formula for sulfuric acid is outside my area of expertise.
Please try a general agent or a chemistry specialist."

Example 3: Cross-domain query (boundary case)

User: "How did the Industrial Revolution affect chemistry?"

Talkie → Intent Classification:
  - Keyword match: "industrial revolution" → american-history (partial)
  - But "chemistry" → general/chemistry
  - LLM classifier: ambiguous → use tiebreaker rules
  - Tiebreaker: route to american-history with note that
    the question has a chemistry component

Domain Agent:
  "The Industrial Revolution (roughly 1760–1840) transformed American
  manufacturing and led to advances in chemical engineering, particularly
  in textile bleaching, steel production, and petroleum refining.
  [Source: wiki/19th-century.md → 'Industrial Revolution']

  However, detailed chemical processes like the Haber-Bosch method
  or sulfuric acid production are outside my expertise. I can
  recommend a chemistry specialist for those details."

Example 4: Query with no RAG result

User: "What did Thomas Jefferson eat for breakfast on July 4, 1803?"

Talkie → Intent Classification:
  - Keyword match: "thomas jefferson", "1803" → american-history
  → Route to american-history

Domain Agent:
  - RAG: memory_search(corpus=wiki, query="Thomas Jefferson breakfast 1803")
  → No relevant results found (score: 0.12 < threshold 0.7)

Answer: "I don't have information about that in my knowledge base.
While I can tell you about the Louisiana Purchase in 1803, I don't
have records of Thomas Jefferson's daily meals."

7. Tradeoffs Analysis

Approach Domain Purity Latency Maintenance Fidelity Auditability Cost
Persona only Low Minimal None Low None $
RAG only High Medium High Medium High $$
Intent classifier only Medium Low Medium Low Medium $
Persona + RAG + Classifier High Medium Medium High High $$
Constrained decoding High Medium Very High Medium Medium $$$
Fine-tuning Highest Minimal Very High Highest Low $$$$

Scoring key: - Domain Purity: How often does the agent stay in domain? - Latency: Additional time per query. - Maintenance: Ongoing effort to keep the system working. - Fidelity: Does the agent give correct answers within its domain? - Auditability: Can you verify the agent used proper sources? - Cost: Infrastructure and operational cost.

When to use each approach

Situation Recommended approach
Quick prototype, low stakes Persona only
Need accurate domain answers RAG only
High volume, need fast routing Intent classifier only (keyword + small model)
Production, high quality needed Persona + RAG + Classifier
Regulated, zero tolerance for drift Fine-tuning + RAG
Local model, full control Constrained decoding

8. Edge Cases

Ambiguous queries

"What's the date?"
"Tell me about the war."
"Who was the first?"

Strategy: If the intent classifier cannot assign a domain with confidence > threshold, route to the general agent or ask a clarifying question. The general agent can be the default non-domain agent.

Cross-domain queries

"How did the discovery of DNA's structure affect civil rights legislation?"

Strategy: Allow cross-domain queries but have the domain agent answer only its portion. The persona prompt should include: "If a question spans multiple domains, answer only the part within your expertise and suggest consulting a specialist for the rest."

User insists on out-of-domain answer

User: "But you're a general AI, you know chemistry. Just tell me."

Strategy: The agent should politely maintain its boundary. The persona + deflect message should be firm but not confrontational:

"I understand you'd like me to answer, but I'm configured as an
American History specialist. I can't answer chemistry questions.
Please ask a general agent or a chemistry specialist."

Knowledge drift

Historical discoveries happen (new archaeological findings, declassified documents, revised historical interpretations).

Strategy: The RAG corpus is the source of truth. When new information emerges:

  1. Update/add wiki markdown files
  2. Recompile the vector index with domain-compile.js
  3. The agent immediately has access to the new knowledge

This is a major advantage over fine-tuning — no retraining needed.

Competing domain matches

"Tell me about the constitutional issues in the Civil War."

This could match both american-history and legal-research.

Strategy: The intent classifier returns confidence scores for all domains. If the top two scores are close (within 0.1), either:

  1. Ask the user to clarify: "I see this could be a history question or a legal question. Which would you prefer?"
  2. Route to the higher-confidence domain
  3. Route to a special "cross-domain" agent if one exists

Empty or non-informative queries

""
"?"
"Hello"
"Thanks"

Strategy: These should not trigger domain routing. Route to general agent for pleasantries, or handle directly in Talkie.
