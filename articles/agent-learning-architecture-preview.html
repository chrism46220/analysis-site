Agent Learning Architecture

A practical design for how Talkie, Plato, and downstream agents can improve over time through structured experience capture, retrieval, and configuration evolution.

1. Design Principles

1.1 Learning = stored experience + retrievable patterns

LLM-based agents cannot update model weights. Learning means:

  • Remembering what worked (and didn't) in past sessions
  • Reusing successful patterns without reinventing them
  • Adapting configuration and prompts based on outcomes
  • Detecting repeated failure modes and routing around them

1.2 Specific > general

Agents learn fastest on repeated, bounded tasks:

  • Deployment workflows
  • Code review patterns
  • Troubleshooting scripts
  • Report generation templates
  • Error recovery sequences

General improvement ("write better code") is aspirational and depends on accumulating many specific learnings.

1.3 No fine-tuning in this stack

Fine-tuning API-based models is not practical here. All learning is configuration-layer and retrieval-layer — not weight-layer.

2. Data Model

2.1 Experience Record

Each stored experience is an atomic record:

{
  id:            uuid
  agent:         "talkie" | "plato" | "manny" | "q"
  task_type:     string (e.g. "deploy", "code_review", "troubleshoot")
  task_hash:     sha256(normalize(input))
  context:      {
    routing:     "talkie->plato->manny->q"
    model:       "deepseek/deepseek-reasoner"
    duration_ms: number
    outcome:     "success" | "failure" | "partial"
  }
  patterns:     {
    key_commands:  string[]
    key_decisions: string[]
    error_signals: string[]
  }
  outcome_note:  free-text summary
  user_feedback: null | "good" | "bad" | "fix: ..."
  tags:          string[]
  created_at:    iso8601
}

2.2 Playbook

A playbook is a versioned, reusable workflow extracted from one or more experience records:

{
  id:            uuid
  name:          "deploy-frontend-v2"
  description:   "Build, test, and deploy the React frontend"
  triggers:      string[]
  steps:         CommandStep[]
  checkpoints:   {step: number, expected: string}[]
  derived_from:  experience_id[]
  version:       semver
  success_rate:  float
  tags:          string[]
  created_at:    iso8601
}

2.3 Preference Profile

Learned user preferences, updated on explicit feedback:

{
  user_id:      "default"
  style: {
    verbosity:  "concise" | "normal" | "detailed"
    tone:       "neutral" | "warm" | "formal"
    format:     "markdown" | "plain" | "structured"
  }
  routing: {
    prefer_fast:    boolean
    prefer_safe:    boolean
  }
  learned_patterns: {
    "request_type": "preferred_agent_route"
  }
  feedback_history: {
    accepted:   number
    rejected:   number
    corrections: string[]
  }
  updated_at:  iso8601
}

2.4 Error Pattern Registry

Learned failure modes and their mitigations:

{
  id:            uuid
  error_signal:  "TimeoutError: npm install"
  match_pattern: "npm install.*ETIMEOUT|npm install.*network"
  context:       "node deployment"
  mitigation:    "Add --prefer-offline flag and retry with 3s backoff"
  hit_count:     number
  last_seen:     iso8601
  resolved:      boolean
}

3. Storage Strategy

All learning data lives in the workspace, using existing OpenClaw primitives. No external database.

3.1 Directory Layout

/home/chris/.openclaw/workspace-talkie/learning/
├── experiences/
│   ├── 2026-05-16-deploy-frontend.json
│   ├── 2026-05-17-code-review-pr42.json
│   └── ...
├── playbooks/
│   ├── deploy-frontend-v1.json
│   ├── deploy-frontend-v2.json
│   ├── code-review-basic.json
│   └── ...
├── preferences.json
├── error-patterns.json
├── reflection-log.json
└── index.json

3.2 Index Schema

The index maps task hashes and trigger patterns to experience IDs for fast retrieval without scanning all files:

{
  "by_task_hash": {
    "a1b2c3...": "experiences/2026-05-16-deploy-frontend.json"
  },
  "by_trigger": {
    "deploy":     ["playbooks/deploy-frontend-v2.json"],
    "code-review": ["playbooks/code-review-basic.json"],
    "npm install": ["error-patterns.json#entry-3"]
  },
  "by_tag": {
    "frontend": ["playbooks/deploy-frontend-v2.json"],
    "network": ["error-patterns.json#entry-3"]
  }
}

3.3 Compiled Wiki Integration

The compiled wiki (corpus=wiki) is the right retrieval mechanism for learning data that needs to be semantically searchable.

On each learning write, auto-append a summary entry to a wiki markdown file:

# Learning Wiki  (auto-compiled)

## 2026-05-16
- Deploy frontend: used `npm ci` — 30s faster
- Error pattern: npm registry timeout — mitigation: --prefer-offline + retry
- User prefers: post-deploy summary in plain text, not markdown

4. Retrieval Strategy

4.1 When to retrieve

TriggerWhat to fetchAgent
Task routing decisionPreference profile, recent similar experiencesTalkie
Execution beginsRelevant playbooks, error patternsPlato
Command failsError pattern registry for signal matchPlato/Manny
Task completesNothing (write happens after)—
Feedback receivedPreference profile (for update)Plato

4.2 How to rank

  1. Exact task-hash match → highest priority
  2. Trigger-pattern match → high priority
  3. Semantic similarity via memory_search(corpus=wiki)
  4. Recency → tiebreaker

4.3 Retrieval packet

When Plato spawns for a task, its subagent context includes:

LEARNING_CONTEXT:
  matching_experiences:  [experience records with same task type]
  matching_playbooks:    [playbooks whose triggers match]
  relevant_errors:       [error patterns matching context]
  preference_profile:    {verbosity, tone, format}

5. Update Strategy

5.1 Experience write (post-task)

Writer: Plato (after task completes and Q verifies)

When: Task completes (success/failure), nontrivial, repeatable type.

Gate: Q verifies accuracy before write.

5.2 Playbook extraction (periodic / on-threshold)

Writer: Plato, during scheduled reflection task.

When: 3+ experiences of same task_type exist.

5.3 Preference update (on feedback)

Trigger: User says "too verbose", "wrong tone", "do this differently".

5.4 Error pattern extraction (on failure)

Process: Identify error signal, check for existing match, add or increment.

5.5 Configuration evolution (human-in-the-loop)

{
  "target": "AGENTS.md",
  "change": {
    "section": "Routing Rules",
    "old": "deploy → always escalate to manny",
    "new": "deploy → check learning/playbooks/deploy-*.json first"
  },
  "rationale": "3 deploy tasks had same npm error; playbook has fix",
  "evidence": ["experiences/2026-05-16-deploy.json", "error-patterns.json#3"]
}

Config changes are drafted by Plato but never applied without user approval.

6. Reflection Engine

A cron-scheduled task (weekly or on-demand) that analyzes experiences, extracts playbooks, and proposes improvements.

{
  "schedule": "0 8 * * 1",      // Monday 8am
  "agent": "plato",
  "task": {
    "type": "reflect",
    "params": {
      "scope": "7d",
      "output": "learning/reflection-log.json"
    }
  }
}

7. Integration with Agent Stack

7.1 Talkie integration

Talkie's AGENTS.md gains one new routing rule: check preferences.json before escalating, and pass user feedback back to Plato.

7.2 Plato integration

Plato's AGENTS.md gains pre-task retrieval, post-task write, and periodic reflection instructions.

7.3 Manny integration

Manny emits structured error information in output packets; it does not read or write learning data directly.

7.4 Q integration

Q verifies experience records, playbooks, and error patterns for accuracy before writes are committed.

8. Worked Example

Frontend deployment fails with npm timeout

With learning:

  1. Talkie routes to Plato with preference profile
  2. Plato checks index → finds playbook + error pattern
  3. Plato prepends mitigation to subagent context
  4. Manny runs deploy — npm hits timeout
  5. Manny applies mitigation → succeeds
  6. Plato writes experience record, updates error hit count
  7. Q verifies the record
  8. Talkie reports success with applied mitigation

Without learning (current behavior):

  1. Plato figures out deploy from scratch
  2. npm times out — tries random fix
  3. Eventually succeeds or fails
  4. No record kept for next time

9. Pragmatic Roadmap

PhaseWhatRisk
1: Capture
Week 1-2		 Create learning/ dir, add post-task write, Q gate Storage growth; prune >90d
2: Retrieve
Week 3-4		 Pre-task retrieval, wiki search, preference wiring Context pollution; start with exact match
3: Extract
Week 5-6		 Playbook extraction, reflection cron, config proposals Playbook rot; version + track success rate
4: Adapt
Week 7+		 Auto-apply mitigations, user approval for config changes Over-automation; human-in-the-loop required

10. What NOT To Do

ApproachReason to avoid
Fine-tune a model on task historyCost, latency, impractical with API models
Store raw conversation logsNoise >> signal, no structure
Let every agent write to learning dataRace conditions, no Q gate
Auto-apply configuration changesMust preserve human-in-the-loop
Semantic search without indexingSlow, unreliable ranking

11. Anti-pattern Detection

  • Playbook rot: success rate drops below 0.5 → flag for review
  • Feedback oscillation: user alternates between extremes → pause updates
  • Error spam: same error 10+ times without mitigation → alert user
  • Experience explosion: 50+ trivial records → auto-prune (limit: 20/type)

12. Success Metrics

MetricTarget
Task success rate+10% after 4 weeks
Retry reduction-30% per-task command retries
User corrections-50% same-type corrections
Time-to-task-complete-20% for repeated tasks
Playbook hit rate>60% of repeat tasks use a playbook

13. Edge Cases & Open Questions

  • Corrupted index? Regenerate by scanning all experiences.
  • Bad experience record? Q gate + reflection outlier detection.
  • Latency? ~200-500ms for pre-task retrieval; ~100ms for post-task write.
  • No learning data? Graceful degradation — skip retrieval, execute normally.

Appendix B: Modified Agent Files

Talkie AGENTS.md additions

## Learning Rule

Before escalating to Plato:
- Read `learning/preferences.json` to check routing preferences
- If preferences.routing.prefer_fast is true, set URGENCY: high
- Attach preference data to handoff packet

After Plato returns:
- If user provides explicit feedback like "too verbose" or
  "that's wrong", include {user_feedback: "..."} in return packet
  so Plato can record it

Plato AGENTS.md additions

## Learning Behavior

### Before planning a task:
1. Read `learning/index.json` for matching experiences/playbooks
2. If match found, read the relevant files
3. Prepend findings as RELEVANT_LEARNINGS
4. Check `learning/error-patterns.json` for context-relevant errors

### After task completion:
1. Write experience record to `learning/experiences/`
2. Update `learning/index.json`
3. Append summary to learning wiki
4. If task failed, check/update `learning/error-patterns.json`

### Reflection schedule:
- Weekly reflection writes to `learning/reflection-log.json`
- Proposes playbooks and config changes (never auto-applied)
